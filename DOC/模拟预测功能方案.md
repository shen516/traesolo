## 1. 背景与目标

### 1.1 定义

**模拟预测 = 对已经安排（已排期、未开赛）的未来赛事进行比分预测。**

用户从 `matches` 表中 `status = 'upcoming'` 的赛事里选择一场（或多场）比赛，
基于融合模型计算胜平负概率、比分分布、总进球分布等，并结合该场赛事的真实竞彩 SP
赔率做奖金/期望值分析。整个过程是**只读推演**，不影响正式预测数据。

### 1.2 现状

系统已具备完整的单场预测能力：

- `GET /api/v1/matches/upcoming` 提供已排期未来赛事的分页列表，支持联赛、日期、关键词过滤
  （`backend/api/matches.py`）。
- `POST /api/v1/predictions/calculate` 支持传入 `match_id` 计算预测并落库；`match_id` 为空时不落库
  （`backend/api/predictions.py`、`backend/services/prediction_runner.py`）。
- 融合引擎按 ELO / 泊松 / xG / 蒙特卡洛四路加权，并生成多场景对照
  （`backend/models/ensemble.py`、`backend/services/analysis_scenarios.py`）。
- `matches` 表已存储竞彩赔率（`odds_spf_*` / `odds_nspf_*` / `odds_bf_json` / `handicap`），
  `odds_snapshots` 表存储赔率时序快照（`backend/db/models.py`）。

但当前预测流程存在以下不足：

- 预测与正式落库流程绑定，用户想"试算"一场未来赛事时无法做到只读推演；
- 预测结果只展示胜平负与 Top 比分，缺少比分概率矩阵、总进球分布、大 2.5 球、双方进球等衍生指标；
- 模型概率与赛事真实 SP 赔率没有并排对照，无法直观看到期望值（EV）与"价值"选项；
- 参数（λ、权重、模拟次数等）由配置固定，无法做假设性微调对照。

### 1.3 目标

新增一个**独立的"模拟预测"页面**，围绕已排期未来赛事：

1. 从未来赛事列表中选择比赛（支持联赛 / 日期 / 关键词过滤）；
2. 对所选赛事实时计算胜平负、比分分布、总进球分布及衍生市场指标；
3. 与模型基线（默认参数）并排对比，展示假设调整带来的概率变化；
4. **奖金计算模式**：将模型概率映射到竞彩玩法（胜平负 / 让球 / 比分 / 总进球），
   优先使用赛事真实 SP 计算单注奖金、期望值（EV）与"价值投注"标记（详见 §5）；
5. **高级选项（可选）**：覆盖 λ、xG、融合权重、主场优势、模拟次数与随机种子等参数做假设推演；
6. **全程只读**：不写入 `predictions` 表、不写 Redis 缓存、不影响正式预测与模型训练数据。

### 1.4 非目标（本期不做）

- 不做模拟投注、资金管理、收益回测（奖金计算模式仅做单场理论奖金/EV 分析，不构成投注流程）；
- 不做自由对阵（主客队必须来自已排期未来赛事，不支持假设性"曼城 vs 拜仁"式沙盘）；
- 不做逐分钟比赛事件推演；
- 不保存用户的历史模拟方案（列为后续扩展）；
- 不修改现有预测的融合算法与权重训练逻辑。

## 2. 现有能力与差距

| 能力 | 现有实现 | 差距 |
| --- | --- | --- |
| 未来赛事列表 | `GET /matches/upcoming`（分页/联赛/日期/关键词） | 可直接复用为赛事选择器数据源 |
| 单场预测 | `predict_teams()` / `predict_for_match()` | 与落库/缓存绑定，无只读推演入口 |
| 融合预测 | `EnsembleModel.predict_from_db()` | 无 λ/xG 覆盖、可调模拟次数、明细输出 |
| 蒙特卡洛 | `MonteCarloSimulator.simulate()` | 仅胜平负 + Top5 比分；无矩阵、进球分布、市场指标 |
| 赛事赔率 | `matches.odds_*`、`odds_snapshots` | 未与模型概率并排做奖金/EV 分析 |
| 前端入口 | 无 | 需新增路由、菜单、页面、权限 |

结论：**不需要重写算法**。只需在融合引擎上增加"可选覆盖参数 + 明细输出"，并新增一个编排服务与独立页面。

## 3. 总体设计

### 3.1 架构与数据流

```text
Simulation.vue（新页面）
   │ 1. GET /matches/upcoming 加载赛事选择器
   │ 2. POST /api/v1/predictions/simulate { match_id, overrides? }
   ▼
api/predictions.py（新增路由，权限校验）
   ▼
services/simulation_service.py（新增编排层）
   │ 1. 校验赛事存在且 status=upcoming
   │ 2. 读取赛事主客队 / 联赛 / ELO / xG / 环境参数
   │ 3. 计算基线预测（默认参数，同种子）
   │ 4. 应用高级选项覆盖参数计算模拟预测
   │ 5. 组装 delta / 警告 / 耗时
   │ 6. 调用 prize_calculator 挂载奖金分析
   ▼
models/ensemble.py（predict 增加可选覆盖参数）
   ├── poisson_model.py（λ 与比分矩阵）
   ├── elo_model.py（ELO 概率）
   ├── xg_model.py（xG λ）
   └── monte_carlo.py（新增 simulate_detailed）
```

### 3.2 关键设计原则

1. **以真实赛事为锚**：模拟预测必须绑定一个 `status='upcoming'` 的 `match_id`，主客队、联赛、环境参数均来自该赛事，不允许自由指定对阵。
2. **生产路径零行为变化**：`predict()` 新增参数全部默认 `None/False`，现有调用不受影响。
3. **只读推演**：不调用 `PredictionService.create_or_update`，不调用 `prediction_cache`，不触发 `record_prediction`。
4. **基线可对比**：基线与模拟使用相同的模拟次数与随机种子，避免随机噪声被误读为参数效果。
5. **模型实例隔离**：xG 子模型是内存共享状态，模拟请求使用独立模型实例或加锁，避免污染并发的正式预测。
6. **参数优先级明确**：显式覆盖 > 赛事/数据库值 > 配置默认值，响应中返回实际生效值。

## 4. 后端设计

### 4.1 新增接口

**`POST /api/v1/predictions/simulate`**

- 权限：`simulation:view` 或 `model:manage`（新增 `RequireSimulation` 依赖）。
- 使用同步 `def`（进入线程池），避免蒙特卡洛阻塞事件循环。
- 不落库、不写缓存、不产生预测历史。

#### 请求体

```json
{
  "match_id": "20261108_500_12345",
  "simulations": 10000,
  "seed": 42,
  "overrides": {
    "lambda_home": null,
    "lambda_away": null,
    "xg_lambda_home": null,
    "xg_lambda_away": null,
    "weights": {
      "elo": 0.30,
      "poisson": 0.30,
      "xg": 0.22,
      "monte_carlo": 0.18
    },
    "poisson_home_advantage": null,
    "league_avg_goals": null,
    "max_goals": 8,
    "weather": null,
    "temperature": null,
    "pitch_condition": null
  }
}
```

字段说明：

| 字段 | 类型 | 默认 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `match_id` | string | - | 必填、存在、`status='upcoming'` | 目标未来赛事；主客队/联赛/环境由赛事决定 |
| `simulations` | int | 10000 | 1000 ~ 50000 | 蒙特卡洛次数 |
| `seed` | int | null | 0 ~ 2^32-1 | 相同输入 + 相同种子结果可复现 |
| `overrides.lambda_home` | float | null | 0.05 ~ 6.0 | 显式 λ（高级选项）；为空时按攻防参数自动计算 |
| `overrides.lambda_away` | float | null | 0.05 ~ 6.0 | 同上 |
| `overrides.xg_lambda_home` | float | null | 0.05 ~ 6.0 | 显式 xG λ；为空时用 xG 模型输出 |
| `overrides.xg_lambda_away` | float | null | 0.05 ~ 6.0 | 同上 |
| `overrides.weights` | object | 配置权重 | 每项 ≥0，总和 >0 | 融合权重；仍受 MC 上下限约束 |
| `overrides.poisson_home_advantage` | float | 配置值 | 0.8 ~ 1.6 | 主场优势系数 |
| `overrides.league_avg_goals` | float | 联赛均值 | 1.5 ~ 4.5 | 联赛进球环境 |
| `overrides.max_goals` | int | 8 | 5 ~ 10 | 比分矩阵上限 |
| `overrides.weather/temperature/pitch_condition` | string | 赛事字段值 | 枚举见 `environment_service` | 环境修正，默认取赛事自身字段 |

### 4.3 计算规则

#### 4.3.1 参数加载

主客队与环境参数一律来自所选赛事，沿用现有逻辑，避免重复实现：

- 主客队：`match.home_team_id` / `match.away_team_id`；
- 球队参数：`EnsembleModel._params_from_orm()`（攻防、xG、联赛、名称）；
- ELO：`Team.elo_rating`；
- 联赛均值：`League.avg_goals`，缺失时用 `config.yaml` 的 `league_avg`；
- 环境：默认取赛事自身 `weather` / `temperature` / `pitch_condition`，可被 overrides 覆盖；
- 分联赛权重/超参：`get_weights_for_league()`、`get_hyperparams_for_league()`。

#### 4.3.2 λ 计算与覆盖优先级

```text
自动 λ：
λ_home = attack_home × defense_away × league_avg × poisson_home_advantage
λ_away = attack_away × defense_home × league_avg

覆盖优先级：
显式 overrides.lambda_*  >  自动计算
环境修正：在 λ 确定后统一乘以 λ_factor（与现有逻辑一致）
```

#### 4.3.3 xG λ 与蒙特卡洛混合

- 未覆盖：沿用现有 `xg_result` 的 λ；
- 显式覆盖：用 `PoissonModel.predict(λ_xg_home, λ_xg_away)` 重建 xG 概率与比分参考，`coverage` 标记为 1；
- MC 混合公式保持现状：

```text
mc_blend = min(0.55, 0.35 + 0.2 × xg_coverage)
mc_λ_home = (1 - mc_blend) × λ_home + mc_blend × xg_λ_home
mc_λ_away = (1 - mc_blend) × λ_away + mc_blend × xg_λ_away
```

- 若 xG 覆盖率为 0 且未显式覆盖：`xg` 权重并入 `poisson`（沿用现有降级逻辑），并写入 `warnings`。

#### 4.3.4 融合权重

- 复用 `_normalize_weights()`；
- 保留 `max_monte_carlo_weight` / `min_monte_carlo_weight` 约束，与正式预测口径一致；
- 若用户设定值被约束调整，`warnings` 中提示"蒙特卡洛权重已按生产约束调整"；
- 返回 `weights_used` 为归一化后的实际值。

#### 4.3.5 蒙特卡洛明细

新增 `MonteCarloSimulator.simulate_detailed(lambda_home, lambda_away, *, simulations, seed, max_goals)`：

- 使用独立 `numpy.random.default_rng(seed)`，不修改共享 RNG；
- 向量化统计：
  - 胜/平/负概率；
  - 比分矩阵（`max_goals × max_goals`）；
  - Top 比分（按概率降序，返回前 8）；
  - 总进球分布（0 ~ 10，10 表示 10+）；
  - 总进球均值/标准差；
  - 大 2.5、大 3.5、双方进球概率。
- 原 `simulate()` 保持不变，供正式预测继续使用。

#### 4.3.6 基线与模拟

| 项目 | 基线 | 模拟 |
| --- | --- | --- |
| 赛事/球队/联赛参数 | 数据库值 | 数据库值 |
| λ | 自动计算 | 覆盖值或自动计算 |
| 权重 | 联赛/全局权重 | 请求覆盖权重 |
| 环境 | 赛事字段值 | 覆盖值或赛事字段值 |
| 模拟次数/种子 | 与请求一致 | 请求值 |
| 结果用途 | 对比参照 | 页面主展示 |

- 两次计算使用同一模拟次数与种子，`delta = simulated - baseline`；
- 基线同样返回 `scenarios`，便于前端展示各模型分量。

### 4.4 并发与状态隔离

问题：`EnsembleModel.xg` 是有状态的内存对象，`_hydrate_xg_from_params()` 会写入球队 xG 数据；直接复用全局单例可能影响并发中的正式预测。

方案（二选一，推荐 A）：

- **A. 独立实例**：`SimulationService` 使用专用 `EnsembleModel` 实例，启动时从 `ensemble_registry.get_ensemble()` 复制 `weights`、`league_weights`、`league_hyperparams`、`global_hyperparams`；每次请求只操作该实例。
- **B. 加锁**：复用全局实例，用 `threading.Lock` 串行化模拟计算；实现简单但会降低并发。

### 4.5 性能与限流

- 10,000 次模拟预计 50~150ms，基线 + 模拟合计 < 500ms；
- 50,000 次模拟上限约 1s，接口层设置 10s 墙钟保护；
- `simulations` 上限 50,000，防止单请求占用过多 CPU；
- 可选：按用户/IP 做简单频率限制（复用现有中间件能力，未实现则记录为后续项）。

## 5. 奖金计算模式设计

模拟预测的核心价值之一是**将模型概率转化为竞彩投注语境下的期望收益**。本节设计"奖金计算模式"，让用户在模拟结果基础上，按竞彩玩法规则计算理论奖金与期望值。

### 5.1 设计目标

1. 基于模拟输出的概率分布，按竞彩 SP 赔率计算各玩法的理论奖金；
2. 支持单关奖金估算（串关需多场，列为后续扩展，见 §12）；
3. 对比模型概率与 SP 隐含概率，标记"价值投注"（模型概率 > 隐含概率）；
4. 全程只读、不产生真实投注，仅作为分析参考。

### 5.2 SP 赔率来源

模拟预测绑定真实未来赛事，SP 来源以**赛事真实赔率为主**，合成 SP 仅作缺失兜底：

| 优先级 | SP 来源 | 说明 |
| --- | --- | --- |
| 1 | 最新赔率快照 `odds_snapshots` | 按 `captured_at` 取该赛事最新一条快照的 `odds_spf_*` / `odds_nspf_*` / `odds_bf_json` |
| 2 | `matches.odds_*` 当前值 | 无快照时用赛事表当前赔率字段 |
| 3 | 合成 SP（兜底） | 某玩法赔率整体缺失时，由模型概率反推：`SP_i = 1 / (P_i × (1 + overround))`，overround 默认 0.13（竞彩典型抽水率），可调 |
| 覆盖 | 手动输入 | 用户可覆盖任意选项的 SP 值（`sp_mode=manual`） |

**玩法级粒度**：SP 来源按玩法独立判定。例如胜平负有真实 SP 而比分 `odds_bf_json` 缺失时，
胜平负用真实值、比分用合成值，`prize.sp_source` 按玩法分别标记（`"real"` / `"snapshot"` / `"synthetic"` / `"manual"`）。

**合成 SP 公式**（仅兜底用）：

```text
raw_i = P_model_i / (1 + overround)    # 含抽水的"公平"概率
SP_i  = 1 / raw_i                       # 对应赔率
```

> 示例：模型主胜概率 0.55，overround 0.13 → raw = 0.55/1.13 ≈ 0.487 → SP ≈ 2.05

### 5.3 支持玩法与选项映射

| 玩法 | 选项来源 | 模拟数据映射 |
| --- | --- | --- |
| 胜平负（SPF） | 3 选项 | `home_win_prob / draw_prob / away_win_prob` |
| 让球胜平负（NSPF） | 3 选项 + 让球数 | 基于比分矩阵偏移计算（见 5.3.1） |
| 比分（BF） | 31 选项 | 比分矩阵 `score_matrix` 聚合（见 5.3.2） |
| 总进球（TG） | 8 选项（0~7+） | `goal_distribution` 直接映射 |

#### 5.3.1 让球胜平负概率计算

让球数 `h`（主让为负、客让为正）**默认取赛事 `matches.handicap` 字段**，用户可手动调整：

```text
P(让球主胜) = Σ P(h_goals, a_goals)  where h_goals - a_goals + h > 0
P(让球平)   = Σ P(h_goals, a_goals)  where h_goals - a_goals + h = 0
P(让球客胜) = Σ P(h_goals, a_goals)  where h_goals - a_goals + h < 0
```

#### 5.3.2 比分选项聚合

竞彩比分共 31 个选项，模拟比分矩阵需聚合：

| 竞彩选项 | 矩阵映射 |
| --- | --- |
| 主胜比分（1:0 ~ 5:2，共 12 个） | 矩阵中对应单元格 |
| 胜其它 | 主胜概率 − 12 个已知主胜比分概率之和 |
| 平局比分（0:0 ~ 3:3，共 4 个） | 矩阵中对应单元格 |
| 平其它 | 平局概率 − 4 个已知平局比分概率之和 |
| 客胜比分（0:1 ~ 2:5，共 12 个） | 矩阵中对应单元格 |
| 负其它 | 客胜概率 − 12 个已知客胜比分概率之和 |

### 5.4 奖金计算规则

遵循竞彩固定奖金规则（参考 `DOC/500竞彩足球页面功能分析.md` §5.1、§8.3）：

#### 5.4.1 单注奖金

```text
单注奖金 = 2 × SP                          （单关）
单注奖金 = 2 × ∏(SP_i)                    （N串1，i = 1..N，后续扩展）
```

#### 5.4.2 单注奖金上限

| 过关方式 | 上限 |
| --- | --- |
| 单关 | 10 万元 |
| 2~3 关 | 20 万元 |
| 4~5 关 | 50 万元 |
| 6 关及以上 | 100 万元 |

#### 5.4.3 最低奖金

单注奖金不足 2 元时补足至 2 元。

#### 5.4.4 总奖金

```text
总奖金 = 单注奖金 × 倍数
总投入 = 注数 × 倍数 × 2 元
```

### 5.5 期望值与价值分析

对每个选项计算期望值（EV），帮助用户识别模型与市场定价的偏差：

```text
EV = P_model × SP × 2 − 2
ROI = EV / 2 × 100%
```

| 指标 | 含义 | 标记规则 |
| --- | --- | --- |
| `P_model` | 模拟模型概率 | - |
| `P_implied` | SP 隐含概率 = `1/SP / Σ(1/SP_j)` | 复用 `odds_analysis.implied_probs_from_sp` |
| `EV` | 每 2 元投注的期望净收益 | EV > 0 标绿，EV < 0 标红 |
| `edge` | `P_model − P_implied` | edge > 2% 标记"价值" |

### 5.8 实现要点

1. **真实与合成 SP 统一结构**：无论来源，`prize` 字段结构一致，前端无需区分渲染逻辑，仅展示 `sp_source` 标记；
2. **快照优先**：读取 `odds_snapshots` 最新一条（按 `captured_at` 降序），无快照回退 `matches.odds_*`；
3. **让球概率从比分矩阵计算**：不引入新模型，直接聚合 `score_matrix`，保证与模拟概率一致；
4. **比分"其它"选项**：用总概率减去已知比分概率，避免矩阵截断导致概率丢失；
5. **EV 计算精度**：概率保留 4 位小数，SP 保留 2 位，EV 保留 2 位；
6. **价值标记阈值**：`edge > 0.02`（2%）标记为价值，可在配置中调整；
7. **串关暂不支持**：单场模拟无法构成串关，串关奖金计算留待"批量模拟"扩展（§12）实现。

## 10. 验收标准

### 10.1 功能

- [ ] 可从未来赛事列表（联赛/日期/关键词过滤）中选择一场赛事并成功模拟；
- [ ] 对 `status` 非 upcoming 的赛事，接口返回 400 且页面提示刷新列表；
- [ ] 展示胜平负、Top 比分、比分热力、总进球分布、大 2.5、双方进球；
- [ ] 手动 λ / xG / 权重覆盖值按预期生效，基线 vs 模拟 delta 展示正确；
- [ ] 未使用高级选项时不展示对比区，结果等价于该赛事的只读重算；
- [ ] 相同输入 + 相同种子，多次请求结果完全一致。

### 10.1.1 奖金计算模式

- [ ] 赛事有赔率快照时，`sp_mode=auto` 返回快照 SP 且 `sp_source` 标记为 `snapshot`；
- [ ] 无快照但有 `matches.odds_*` 时，回退真实值且标记为 `real`；
- [ ] 玩法赔率缺失时，合成 SP 兜底且 `SP_i ≈ 1 / (P_i × (1 + overround))`；
- [ ] 手动覆盖 SP 后，EV 与价值标记按新 SP 重算；
- [ ] 让球数默认取赛事 `handicap`；让球三路概率之和为 1，且与比分矩阵聚合结果一致；
- [ ] 比分 31 选项概率之和 ≈ 1（含胜/平/负其它兜底）；
- [ ] 单注奖金 = 2 × SP，超过上限时截断到上限，不足 2 元补足；
- [ ] `edge > 2%` 的选项被标记为价值，其余不标记；
- [ ] 奖金计算全程不写库、不产生投注记录。

### 10.2 安全与只读

- [ ] 调用 20 次模拟后，`predictions` 表行数不变；
- [ ] Redis 中无新增 / 修改预测缓存；
- [ ] 无 `simulation:view` 且无 `model:manage` 的用户访问接口返回 403，菜单不可见。

### 10.3 性能

- [ ] 10,000 次模拟单次请求 P95 < 1s（本地环境）；
- [ ] 50,000 次模拟不超过 10s 墙钟上限；
- [ ] 页面首次渲染无阻塞，图表在结果返回后渲染。

### 10.4 兼容性

- [ ] 现有赛事详情页预测、批量重算、模型管理功能不受影响；
- [ ] 默认参数下 `/predictions/calculate` 输出字段与行为保持不变。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| xG / ELO 内存状态被并发污染 | 正式预测结果抖动 | 模拟使用独立模型实例（推荐）或加锁 |
| 权重被 MC 上下限调整，用户困惑 | 输入与结果不一致 | 响应返回 `weights_used` + 警告提示 |
| 赛事赔率缺失或过期 | 奖金/EV 参考价值下降 | 快照 → 赛事赔率 → 合成兜底三级回退，页面标注 `sp_source` 与快照时间 |
| 大模拟次数导致 CPU 占用 | 影响其他请求 | 上限 50,000 + 同步线程池 + 可选限流 |
| 比分矩阵维度大 | 响应体膨胀 | 默认 8×8，前端仅展示 0~5 球并聚合 |
| 赛事临近开赛时赔率变动快 | 模拟时 SP 与投注时不一致 | 奖金分析展示快照时间戳，提示赔率时效性 |
| 用户误读为投注建议 | 合规风险 | 奖金分析区固定展示"仅供分析参考，不构成投注建议"免责文案 |

## 12. 后续扩展（P1+）

1. **批量模拟与串关奖金**：一次选择多场未来赛事批量模拟，支持 2串1 ~ 8串1 的串关奖金计算与敏感性曲线（如 λ 每 +0.1 的胜率变化）；
2. **方案保存与分享**：保存赛事 + 参数组合、生成对比链接；
3. **历史回测联动**：用已完赛赛事验证某组参数在样本上的 Brier / 命中率；
4. **球员缺阵因子**：接入伤停数据，将关键球员缺阵折算为攻防系数；
5. **赔率变动对照**：将模型概率与多时点快照的 SP 隐含概率并排展示，辅助寻找偏差。
