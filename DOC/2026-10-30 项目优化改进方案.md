## 二、整体评估（结论先行）

项目在**数据采集、模型融合、RBAC、竞彩分析、调度与长任务**等域已经相当成熟，有清晰的域拆分、完整测试与专项 skill 规范。以下问题按严重程度分级：

- **🔴 高风险 / 必改**：训练作业不校验用户状态、生产弱口令、git 尚未首次提交、`.gitignore` 验证不足、孤儿路由 `/predict`、`on_event` 弃用。
- **🟠 中风险 / 应改**：`training_service.py` 上帝模块、探针脚本未清理、审计日志静默 `except`、启动期查询未批量化、前端 `API_BASE_URL` 硬编码。
- **🟡 低风险 / 可改**：文档与需求不一致、`requirements.md` 未落地愿景、缺 CI、缺类型检查、缺前端单测。

## 三、问题清单与优化方案

### 🔴 P0 —— 安全与工程基线（优先处理）

#### 1. 训练作业校验用户状态（实际安全风险）

**现状**：`services/training_service.py` 中**没有** `user.is_active` 检查。已排队但提交者被禁用的训练会继续跑并写 `model_versions` / `training_records`，最长窗口约 2h（`job_queue.default_timeout` 默认 7200s）。

**方案**：
- 在 RQ 作业执行入口（`services/jobs/tasks.py` 的 `run_training_job`）与 `train_all` 主循环每轮开头各查一次 `user.is_active`（通过 `train_lock.get_queued_user()` 取提交者 ID）。
- 命中禁用 → 抛可识别异常（复用 `TrainingAborted` 或新增 `TrainingUserDisabled`），置 `JobStatus.CANCELLED` 并**停止权重落库**。
- RQ 作业状态里的 `exc_info` 保持 `None`，别把内部异常文本回给客户端。

**涉及文件**：`services/training_service.py`、`services/jobs/tasks.py`、`services/train_lock.py`（补充 `get_queued_user`）。
**回归**：新增测试——建用户→入队训练→禁用→断言训练被中止且未写 `model_versions`。

#### 2. 生产弱口令（部署阻塞项）

**现状**：`init_db.py` 每次启动都会创建/对齐默认超管 `admin/admin123`，代码里没有强制换密码机制（已改为软提示 + 顶栏下拉入口，但生产仍会用弱口令启动）。

**方案**：
- 生产用环境变量注入：`TRAESOLO_ADMIN_PASSWORD`，`init_db.py` 读到则使用，否则开发默认。
- 或：`init_db.py` 检测 `TRAESOLO_PRODUCTION=1` 且密码仍为默认时**拒绝启动**（fail-fast）。
- `docker-compose.yml` 的 `model-api` 服务增加 `TRAESOLO_ADMIN_PASSWORD: ${ADMIN_PASSWORD:-}` 映射，部署手册说明必须设置。

#### 3. Git 仓库尚未首次提交 + `.gitignore` 验证

**现状**：仓库 `No commits yet`，全部 Untracked。`.gitignore` 已挡 `backend/venv/`、`backend/.venv/`、`node_modules/`、`frontend/dist/`、`backend/logs/`、`__pycache__/`、`.env` 等，但**从未实际提交验证过**。

**方案**：
1. 先跑 `git status --untracked-files=all` 确认不含 `.venv`、`node_modules`、`__pycache__`、`*.pyc`。
2. 清理探针脚本（见 P1-5）后再做**首次提交**。
3. 建立 `.gitignore` 增补清单：`*.log`、`backend/_*.py`、`backend/*_check.py`、`backend/football_data.db`、`.pytest_cache/`、`.cursor/`（可选，视团队是否共享 skill）。
4. 首次提交建议分成几个逻辑 commit：`chore: init repo scaffold` / `feat: backend api & models` / `feat: frontend` / `feat: crawler & scheduler` / `docs: DOC & skills`，便于后续 `git log --oneline` 审阅与 blame。

#### 4. `/api/v1/predict` 孤儿路由收编

**现状**：`main.py:190` `@app.post("/api/v1/predict", dependencies=[RequirePredictionCalc])` 直接挂在 app 上，绕过 `api/__init__.py` 的 router 注册。前端 `frontend/src/api/prediction.js:31` 仍在用 `compute` → `POST /predict`。

**方案**：
- 前端若已统一走 `/predictions/calculate`（`prediction.js:12`），让 `compute` 改调 `/predictions/calculate`，然后删除 `main.py` 的孤儿路由。
- 否则把该路由迁入 `backend/api/predictions.py`，注册进 `api/__init__.py`，保持 `/api/v1/predict` 原路径（注意 router 前缀拼接后不能多出一段 `/predictions`）。
- 权限沿用 `RequirePredictionCalc`。迁移后跑一遍前端双队预测流程验证。

#### 5. `on_event` 弃用改为 lifespan

**现状**：`main.py:243,289` 使用 `@app.on_event("startup")` / `@app.on_event("shutdown")`，触发 FastAPI 弃用警告（后续版本将移除）。

**方案**：改为 `@asynccontextmanager` + `app = FastAPI(lifespan=lifespan)`，把现有 startup/shutdown 逻辑迁入。注意 `TestClient` 的 `with` 上下文会自动触发 lifespan，与现有 conftest 兼容。改后跑全量测试确认无行为差异。

### 🟠 P1 —— 代码质量与性能（尽快处理）

#### 1. 拆分 `training_service.py`（上帝模块，约 2144 行）

**现状**：训练执行、锁续期、权重平滑、超参搜索、walk-forward 全在一个文件（99606 字节）。改一处极易碰坏其它，且测试/审查成本高。

**方案**（按域拆，保持对外 import 面不变，`api/models.py`、`worker.py` 只改最少）：

```
services/training_service.py   →  门面/编排，保留既有公共函数签名
services/train/executor.py     →  训练主流程与数据切分
services/train/smoothing.py    →  权重 EMA 平滑
services/train/hyperparam.py   →  超参网格搜索（ELO K/主场、泊松主场、四维权重）
services/train/walkforward.py  →  walk-forward 验证与指标
services/train/lock.py         →  锁申请/续期（已有 services/train_lock.py，避免重复造）
```

**注意**：模块间通过现有 `training_service` 的类实例/状态共享，拆分时需把 `TrainingService` 的公共方法保留为门面委托。改完必须全量测试绿。

#### 2. 清理探针脚本

**现状**：
- 仓库根（6 个）：`check_goals_data.py`、`check_players.py`、`clean_wc_players.py`、`run_wc_player_crawl.py`、`test_player_crawl.py`、`test_teams.py`。
- `backend/` 根（约 13 个）：`_probe_imgs.py`、`_probe_img_urls.py`、`_probe_league_logo.py`、`_500_ajax_probe.json`、`_imgs.txt`、`_test_api.py`、`_test_cors.py`、`_test_dashboard_api2.py`、`_test_dashboard_api3.py`、`_test_logs_debug.py`、`_test_logs_error.py`、`check_wc_data.py`、`football_data.db`（0 字节占位）。

**方案**：
- 确认是历史一次性脚本后删除；`backend/tests/` 下的是正式 pytest，**别删**。
- 建立约定：临时脚本一律 `backend/_xxx_check.py` 且用后删除，勿留仓库根；探针产物不入 git。
- 若担心误删，先移动到 `backend/_archive/`（git 忽略）观察一个迭代周期再删。

#### 3. 审计日志静默 `except` 改 `warning`

**现状**：审计类兜底仍 `except Exception: pass`，静默失败等于没记录。

**涉及点**（逐条判断）：
| 文件:行 | 说明 | 建议 |
|---------|------|------|
| `main.py:118` | prometheus + access log 兜底 | ⚠️ 改 `logger.warning`（否则监控静默失效） |
| `api/users.py:288,377` | `AUDIT user.create` / `reset_password` | ⚠️ 改 `logger.warning` |
| `api/predictions.py:157` | 当前模型版本兜底回退 `"v5.0.3"` | ⚠️ 改 `logger.warning` |
| `services/crawler_service.py:1875,1915` | 采集兜底 | ⚠️ 采集失败应有日志 |
| `services/scheduler_service.py:168` | 调度兜底 | ⚠️ 改 `logger.warning` |
| `services/training_service.py:252,272,2091` | 联赛/参数兜底 | 可保留（有 fallback 返回值） |
| `services/task_run_lock.py:115,131`、`train_lock.py:143` | 锁兜底 | ⚠️ 锁失败改 `warning` |

#### 4. 启动期查询批量化

**现状**：`main.py:24-33` 启动顺序 `metadata.create_all` → `ensure_schema()` → `init_database()`。`ensure_schema` 逐表 `has_table` + `inspect` 单表查列；多列增量时 round-trip 线性增长。`init_db.py`（约 5 万字节）内部含大量联赛/角色种子插入，未做批量。

**方案**：
- `ensure_schema`：一次 `inspect(engine).get_columns(table)` 缓存列集合后在内存比对，缺失列一次性 DDL（可复用现有 `_add_column_if_missing` 逻辑但先批量收集）。
- `init_db.py`：种子数据用 `executemany` / 批量 upsert（`INSERT ... ON DUPLICATE KEY UPDATE`），避免逐行 commit。
- 衡量：启动耗时（当前本地 MySQL 启动应 < 3s，若 > 5s 优先做）。

#### 5. 前端 `API_BASE_URL` 硬编码

**现状**：`frontend/src/api/http.js` 的 `API_BASE_URL` 开发写死 `http://localhost:8000/api/v1`；生产经 Nginx `/api/` 代理。

**方案**：
- 用 `import.meta.env.VITE_API_BASE_URL ?? "/api/v1"`，配合 `.env.development`（`http://localhost:8000/api/v1`）与 `.env.production`（`/api/v1`）。
- Nginx 已代理 `/api/`，生产直接用相对路径即可，消除跨域与写死端口。
- `main.js` 或 `http.js` 增加运行时校验：缺失时打 `console.warn` 并回退 `/api/v1`。

#### 6. 前端 lint 基线收敛

**现状**：`package.json` 的 `lint` 允许 `--max-warnings 200`，说明当前警告较多（可能历史遗留）。

**方案**：
- 先跑 `npm run lint` 统计警告分布，按文件分组处理；把 `--max-warnings` 逐步下调（200 → 100 → 50 → 0）。
- 新增 `npm run lint:ci`（`eslint . --max-warnings 0`），作为 CI 门禁。

### 🟡 P2 —— 工程化与可维护性（持续改进）

#### 1. 建立 CI（GitHub Actions / 本地 pre-commit）

**现状**：无 CI、无 pre-commit 钩子；后端测试命令依赖 Windows 环境变量与 `-X utf8`。

**方案**：
- 新增 `.github/workflows/ci.yml`：两个 job —— `backend`（Python 3.12，`pip install -r requirements.txt`，`pytest -q -p no:warnings`，SQLite 测试库）与 `frontend`（`npm ci && npm run build && npm run lint:ci`）。
- 因测试依赖 SQLite + 禁用 Redis/调度，需在 workflow 设置 `DATABASE_URL=sqlite:///...`、`RUN_SCHEDULER=0`、`TRAESOLO_REDIS_DISABLED=1`、`TRAESOLO_DISABLE_DOCS=1`。
- 可选：`.pre-commit-config.yaml`（black + isort + eslint + pytest smoke），或 Git hooks 脚本。

#### 2. 后端类型检查 / 格式化

**现状**：无 `mypy`/`ruff` 配置；模型层用 NumPy/SciPy 类型不严格。

**方案**：
- 引入 `ruff`（lint + format），配置 `pyproject.toml`，先 `ruff check --select E,F` 收敛存量，再开 `I`（isort）/ `UP`（pyupgrade）。
- 不强制 mypy（NumPy/SciPy 类型较重），可后续对 `services/` 增量标注。

#### 3. 文档与需求一致性

**现状**：`requirements.md` 含大量**未落地愿景**（InfluxDB、RabbitMQ、K8s、微服务、HTTPS、PDF/Excel 导出、推送、位置级 xG、伤停天气完整闭环等），与已实现架构（FastAPI + MySQL + Redis + RQ + 单体部署）存在出入。

**方案**：
- 在 `requirements.md` 顶部加醒目声明：**「愿景文档，非当前实现；实现以代码与 `DOC/` 为准」**（与 `DOC/功能分析.md` 声明一致）。
- 将「未落地」项收敛到单独章节「未来路线（未实现）」，标注优先级与依赖，避免误导新人。
- 定期（每迭代）核对 `DOC/` 与代码差异，保持文档随代码演进。

#### 4. 前端单测与组件测试

**现状**：前端无任何测试；仅靠 ESLint + 手动验证。

**方案**：
- 引入 Vitest + @vue/test-utils，先对纯逻辑模块写单测：`utils/permissions.js`、`utils/adapters.js`、`utils/matchMeta.js`、`composables/useMatchListFilters.js`、`views/model/modelFormatters.js` 等（纯函数，易测）。
- 组件级测试聚焦高风险页面：`Login.vue`（验证码 hex→base64）、`AppHeader.vue`（权限菜单）、`MatchDetailPrediction.vue`。
- 作为 CI 一部分（`npm run test:unit`）。

#### 5. 监控与可观测性完善

**现状**：已有 `prometheus-client`（`/metrics`）、`metrics_service.py`、`health_service.py`、`app_log_service.py`（JSON 日志）。但无 Grafana 面板模板、无慢查询日志、无 SQLAlchemy 执行统计。

**方案**：
- 提供 `grafana/dashboard.json` 模板（API QPS、错误率、p95 延迟、采集成功/失败、训练耗时）。
- 开启 SQLAlchemy `echo`（仅 `TRAESOLO_SQL_ECHO=1`）或 `event.listen(engine, "before_cursor_execute")` 记录慢 SQL（> 200ms）。
- 在 `health_service` 增加依赖检查：Redis、MySQL、队列深度、调度心跳。

#### 6. 部署与备份

**现状**：`docker-compose.yml` 的 MySQL 数据卷 `mysql-data` 无备份机制；无环境区分（dev/prod）。

**方案**：
- 增加 `scripts/backup_mysql.sh`（`mysqldump` 定时 + 保留 N 天），或部署时用 `docker exec` 定时备份。
- 增加 `.env.production.example` 与部署文档，明确 `DATABASE_URL`、`REDIS_URL`、`TRAESOLO_ADMIN_PASSWORD` 用环境变量注入，**不写死密码进仓库**。
- 生产 Nginx 增加 HTTPS（证书挂载 + `server` 块），`frontend/nginx.conf` 预留 `listen 443 ssl` 模板。

## 五、回归约束（每项改完必查）

- **测试必须全绿**：基线 `198 passed, 1 skipped`。命令：
  ```bash
  cd backend
  $env:TRAESOLO_REDIS_DISABLED="1"; $env:RUN_SCHEDULER="0"; $env:TRAESOLO_DISABLE_DOCS="1"
  .\.venv\Scripts\python -X utf8 -m pytest tests -q -p no:warnings -p no:cacheprovider
  ```
- **`-X utf8` 在 Windows 必须加**：否则 pytest 按 GBK 解码 stdout，中文断言误报（报成 `'??' in '验证码已过期'`）。别去改 API 文案迁就编码。
- **改文件不用 `Set-Content` / `Get-Content -replace` 覆写**：PowerShell 默认破坏 UTF-8 中文（静默变 `?`）。编辑一律走编辑器/文件写入工具。
- **测试里建/删用户**：`db.delete(user)` 前必须先删外键引用行（`UserFavorite`、`UserHistory`、`UserPreference`、`OperationLog`、`UserRole`、`SubscriptionRecord`，按 `user_id` 过滤）；`OperationLog` 没有 `operator_id` 字段。
- **CORS 必须在鉴权中间件之后注册**（成为最外层），否则 401 无 CORS 头。
- **改用户 `is_active` 的入口必须配 `revoke_by_user`**；禁止管理员禁用自己。
- **`token_store` / `captcha_id` 用 `secrets`**，不要用 `time.time()` 参与生成。
- **提交前** `git status --untracked-files=all` 确认不含 `.venv`、`node_modules`、`__pycache__`。
